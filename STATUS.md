## What it does
- Auth (MyTeam pattern): first registration = owner; afterwards invite-only, invites can be bound to one phone/email; password login (PBKDF2), PIN kept for the kiosk clock-in endpoint; sessions 30 days. Email-code verification via Resend activates automatically if `RESEND_API_KEY` is ever set as a Worker secret (not set at launch — phone registrations and classic flow work without it).
- Roles: owner / director / manager / staff. Hourly rates and pay totals are owner-only — the server never includes them in other actors' payloads (verified in tests and in the production smoke).
- Dashboard (NY time): revenue today / last 7 days from served orders, open orders by location, low-stock alerts (stock ≤ min), who is clocked in now.
- Locations: the 4 seeded points (Sunny Isles, Miami Downtown, Fort Lauderdale active; Hallandale opening), CRUD for manager+.
- Team: employees, invites, clock in/out (app + kiosk by id+PIN), timesheet with hours and owner-only pay by rate.
- Kitchen & stock: ingredients (unit, min, stock, cost/unit), recipe cards per dish with live dish cost and food-cost % of price, purchases, write-offs, stocktakes (diff recorded, stock set to actual).
- Purchase documents (2026-10-22, migration `0002`): a purchase is now a document — header (supplier, invoice date, comment, attached invoice photo) + any number of lines. Posting adds stock per line and refreshes unit cost (total ÷ qty), same math as before. The legacy single purchase (`POST /api/purchases`) creates a one-line document, and the `purchases` table remains the line ledger (gained `document_id`), so reports/dashboards are unchanged; pre-existing purchases were backfilled into one-line documents. API: `POST/GET /api/purchase-documents`, `GET /api/purchase-documents/:id/photo` (manager+; the list never embeds the photo, only `hasPhoto`).
- Invoice scan (client-side only): «📷 Сканировать счёт» in the Purchases card — photo (camera on mobile) is downscaled on a canvas to max 1600 px, OCR runs in the browser with Tesseract.js (eng+rus, loaded from CDN on first use, no external AI keys), lines are parsed by `public/purchase-parse.js` (name, qty, unit lb/kg/g/pcs/л…, amount; thousands separators and comma decimals handled) and matched fuzzily to existing ingredients. The result is an editable draft: per line the ingredient is a dropdown (or "+ create new ingredient" inline), qty and line total are editable, lines can be added/removed; only «Провести закупку» posts it, with the downscaled JPEG (~q0.72) stored on the document (`photo_jpeg`, server cap ≈950K base64 chars). UI states honestly that recognition can err and every line must be checked. Purchase history lists documents (date, supplier, total, posted by, 📷 photo viewer).
- Orders: board for tables 1–10 / takeaway / delivery; status chain new → cooking → ready → served (cancel allowed); on "served" the recipe ingredients are deducted and the total counts into revenue. Stopped menu items cannot be ordered.
- Menu: CRUD + stop flag; seed = the real 26 items/prices from the SHAWA GRILL order app.
- Settings: company name (owner); Clover — see below.
- Clover integration (2026-10-22, migration `0003`): **per-location** Merchant ID + API token (Settings → «Clover по точкам», owner-only editing; the token lives server-side and the API never returns it — only state: connected / merchant name / last sync / last error). The old global Merchant ID + token remain as a fallback for locations without their own credentials. Check button = `GET /v3/merchants/{mid}` and stores the verified merchant name; 401/403/404/429 come back as plain-language owner messages. Sales sync: manual «Синхронизировать» per location (manager+) **and the worker cron every 15 min** — paid orders since the location's watermark are upserted by `clover_order_id` (`source='clover'`, status served, total from Clover in cents→$), lines are matched to dishes by `clover_item_id` then by name, unmatched lines stay text positions so revenue is never lost; stock is deducted once per order via the `stock_deducted` flag (same idempotent write-off as app orders). Today's Clover sales show on the orders board with a «Clover» badge and no kitchen buttons; the dashboard revenue counts them. Menu publishing (owner, per location): creates Clover items for unmapped dishes, updates mapped ones, stopped dishes are pushed as unavailable/hidden, mapping stored in `menu_items.clover_item_id`, summary returned (created/updated/per-item errors). API base is `env.CLOVER_API_BASE` (default `https://api.clover.com`; tests point it at a mock). **No live Clover credentials exist yet** — Muhammad enters each point's Merchant ID + token himself; for the Mangal points the tokens depend on the Clover password reset (partner window 2026-10-23).
- 3D location view (2026-10-23, migration `0004`): every location card (Home «open orders by location» and Settings → locations) has a «🧊 3D» button opening a full-screen 3D view of the restaurant — the Mangal café layout ported from the approved `shawa-3d` prototype (`public/scene3d.js`, Three.js r128 from CDN, lazy-loaded like Tesseract): L-shaped counter, open kitchen with a rotating shawarma spit, menu screens, entrance fridge, tables with orange banquettes, greenery, MANGAL sign; animated staff walk role routes, raycast click (or sidebar row) opens the employee card.
